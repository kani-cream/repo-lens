# Milestone v0.4 — Language Providers

> **前倒し実施（2026-08-15）**: Go Provider は v0.1 完了直後に着手する
> （経緯は [README](./README.md) の「実施順序の変更」を参照）。
> Provider SPI の基盤（`CodeStructureProvider` 拡張ポイント、optional
> dependency 分離、言語非依存の `CodeStructure` モデル）は v0.1 の
> UAST 実装時に導入済み。JS/TS Provider と capability UI は元の順序のまま。

## Goal

Repo Lens の Analyzer Provider 構造を実証し、Java / Kotlin 以外の言語へ構造解析を拡張する。

**第一優先対象は Go、次に JavaScript / TypeScript** とする。

v0.4 の目的は対応言語数を増やすことだけではない。Repo Lens 本体に単一の「対応言語」制限を持たせず、IntelliJ 上で利用可能な言語機能と Repo Lens の Language Provider を組み合わせて、Analyzer ごとに capability を追加できる拡張モデルを完成させる。

## Language support policy

Repo Lens は次の二層構造で言語を扱う。

### Universal analyzers

言語固有 AST を必要としない Analyzer は、IntelliJ がテキストファイルとして扱えるプロジェクトで可能な限り利用できる。

主な対象:

- Large File
- TODO / FIXME
- Local Changes
- Branch Diff
- Large Diff
- Git history metrics
- Hotspot の言語非依存部分

### Language providers

クラス、関数、メソッド、引数、ネスト、参照、依存関係などの構造解析は、対象言語の PSI / language API と Repo Lens 側の Provider が利用可能な場合に実行する。

Language Provider が存在しない、または必要な language plugin が利用できない場合でも Repo Lens 本体は停止しない。利用可能な Analyzer のみ実行し、利用不可の capability は理由付きで表示する。

## Deliverables

### Provider architecture

- 言語別 Analyzer Provider の明確な SPI
- Provider の availability 判定
- 言語 plugin が存在しない環境でも Repo Lens 本体が動作する構造
- Analyzer ID / Finding schema / Settings の共通化
- Provider ごとの capability 表示
- `supports()` による Analyzer 単位の実行可否判定
- Provider 固有 API を core / UI から隔離する adapter 層

想定構造:

```text
Repo Lens Core
├─ Universal Analyzers
│  ├─ Large File
│  ├─ TODO / FIXME
│  └─ Git analyzers
├─ UAST Provider
│  ├─ Java
│  └─ Kotlin
├─ Go Provider
│  └─ Go PSI / language API
└─ JS/TS Provider
   └─ JavaScript / TypeScript PSI / language API
```

## Go Provider — first priority

Go は v0.4 の最初の Language Provider 実装対象とする。

最低限、以下の構造チェックを対象とする。

- Large Function
- Large Method
- Too Many Parameters
- Deep Nesting

追加候補:

- import / package dependency evidence
- Unused Candidate の Go 対応
- Circular Dependency の package 情報連携

追加候補は利用できる API の安定性と v0.2 Analyzer の再利用性を確認して段階的に実装する。

Go には Java の class と同一概念を前提としない。言語差を無理に共通モデルへ押し込まず、`Function` / `Method` / package など Go の構造に合わせた Finding を生成する。

### Go implementation checkpoint

JS/TS Provider へ進む前に、Go Provider を用いて次を確認する。

- core / UI を変更せず Provider を追加できたか
- Provider がない環境でも Repo Lens が起動するか
- Universal Analyzer と Go Analyzer の結果を同じ Findings UI に統合できるか
- Navigation / Copy for AI が Java/Kotlin と同じワークフローで機能するか

この checkpoint により Provider architecture の言語非依存性を先に検証する。

## JavaScript / TypeScript Provider

Go Provider で SPI を検証した後、JavaScript / TypeScript を追加する。

最低限、以下の構造チェックを対象とする。

- Large Class 相当
- Large Function / Method
- Too Many Parameters
- Deep Nesting

JavaScript / TypeScript 固有構文を Java/Kotlin の意味へ無理に変換せず、Provider 側で差異を吸収する。

対象 fixture には以下を含める。

- JavaScript function
- class / method
- arrow function
- TypeScript class / method
- JSX / TSX
- nested callback

## Capability model

Tool Window または Settings から、現在の環境でどの Analyzer が利用可能か確認できるようにする。

例:

| Language | Universal | Structure | Reference | Dependency |
|---|---|---|---|---|
| Java | Yes | Yes | Yes | Yes |
| Kotlin | Yes | Yes | Yes | Yes |
| Go | Yes | Yes | Phased | Phased |
| JavaScript | Yes | Yes | Limited / Phased | Limited / Phased |
| TypeScript | Yes | Yes | Limited / Phased | Limited / Phased |
| Other text language | Yes | Provider dependent | Provider dependent | Provider dependent |

この表は製品全体の「対応 / 非対応」を表すものではなく、Analyzer capability を表す。

## Copy / Navigation consistency

新しい Provider でも以下の UX を維持する。

- 同じ Finding list に表示
- 同じ Severity / filter 操作
- file / symbol / range Navigation
- Copy Result
- Copy with Code
- Copy for AI

Provider 固有情報が必要な場合は `metadata` と Detail 表示で補足し、共通 Finding フォーマットを破壊しない。

## Provider diagnostics

- Analyzer が利用できない理由を表示できる
- 必要な language plugin がない場合をエラー扱いしない
- Unsupported syntax は安全に skip する
- Provider 単位の解析時間をログで確認可能にする
- Provider の availability と capability を Settings / Tool Window から確認できる

## Implementation order

1. Language Provider SPI / capability model を確定
2. Go Provider skeleton
3. Go Large Function / Method
4. Go Parameter Count
5. Go Deep Nesting
6. Go fixture / Navigation / Copy for AI の確認
7. Provider architecture checkpoint
8. JavaScript / TypeScript Provider skeleton
9. JS/TS structure analyzers
10. mixed-language project smoke test

## Acceptance Criteria

- [ ] Repo Lens 本体に単一の対応言語制限がない
- [ ] Analyzer ごとに `supports()` / capability を判定できる
- [ ] Language Analyzer Provider を追加できる明確な SPI がある
- [ ] Go Provider が実装されている
- [ ] Go の function / method size を検出できる
- [ ] Go の parameter count を検出できる
- [ ] Go の nesting を検出できる
- [ ] Go Provider がない環境でも Repo Lens 本体が起動できる
- [ ] JavaScript / TypeScript Provider が実装されている
- [ ] JS/TS の function / method size を検出できる
- [ ] JS/TS の parameter count を検出できる
- [ ] JS/TS の nesting を検出できる
- [ ] Universal Analyzer と言語別 Analyzer の結果が同じ UI に統合される
- [ ] Finding から Go / JS / TS の対象位置へ Navigation できる
- [ ] Copy for AI が Java/Kotlin と同じ基本形式で動作する
- [ ] Provider capability をユーザーが確認できる
- [ ] 利用不可 Analyzer の理由を確認できる
- [ ] v0.3 までの主要機能が回帰していない
- [ ] Plugin Verifier と対象 IDE の smoke test が通る

## Test focus

### Go

- package / import
- free function
- receiver method
- parameter count
- nested `if` / `for` / `switch` / function literal
- mixed generated / test files
- Go Provider availability の有無

### JavaScript / TypeScript

- JavaScript function / class / arrow function
- TypeScript class / method / interface 周辺
- nested callback
- JSX / TSX
- provider plugin の有無

### Cross-language

- Java / Kotlin / Go が混在する project
- Go / JS / TS が混在する project
- Provider がない言語で Universal Analyzer のみ動作すること
- Unsupported syntax の安全な skip

## Optional work

v0.4 の必須条件を満たした後、実装コストと利用可能な Public API を見て以下を検討する。

- Python Provider
- Scala / Groovy 等の追加 capability
- その他 JetBrains IDE / language plugin への展開

## Non-goals

- 全言語で完全に同じ解析精度を保証すること
- IntelliJ が認識する全言語へ自動的に構造解析を提供すること
- 独自 parser の大量実装
- IDE 内の全 language plugin への一括対応
- Provider ごとの独自 UI を増殖させること

## Exit review

まず Go の実 Repository で Provider architecture を検証し、その後 Java/Kotlin / Go / JS/TS が混在する Repository で使用する。

新しい言語 Provider を追加するたびに core / UI の大幅変更が必要になる場合は、v1.0 前に SPI を再設計する。逆に、Provider 側の追加だけで Analyzer / Navigation / Copy の一連の操作が成立する状態を v0.4 の成功条件とする。
