# Milestone v0.3 — Git-aware Review

## Goal

Repo Lens を単なるコード構造ビューから、**変更内容と変更履歴を考慮してレビュー優先度を判断できるツール**へ拡張する。

## Deliverables

### Branch Diff Scope

- base branch と現在 branch の差分を Scope として選択可能にする
- 変更ファイルだけを解析対象にできる
- added / modified / deleted の状態を識別する
- base branch が取得できない場合は理由を表示する

### Large Diff

- ファイル単位の追加・削除行数を取得する
- configurable threshold を超えた変更を Finding として表示する
- Detail で changed lines を確認できる
- Copy for AI に diff metrics を含める

### Git history metrics

- Change frequency
- Author count
- 最終更新時点
- TODO/FIXME の経過情報を取得可能な構造

履歴情報は「品質の良し悪し」を断定するためではなく、レビュー優先度を決める Evidence として扱う。

### Long-lived TODO

- TODO/FIXME Finding と Git history を関連付ける
- 最終更新または導入時点を可能な範囲で取得する
- 一定期間以上残っている Marker をレビュー候補として識別できる
- Git 情報を取得できない場合は通常の TODO/FIXME Finding として扱う

### Hotspot

初期定義は次の組み合わせを基本とする。

- 変更頻度が高い
- 構造的 Finding が存在する
- 必要に応じ diff size / author count を補助指標とする

Hotspot score は説明可能であることを優先し、ブラックボックスなスコアリングにしない。Detail ではスコアの構成要素を確認できるようにする。

### UI

- Scope に Branch Diff を追加
- Git metrics 用の列または Detail section
- Hotspot filter / sort
- changed files の状態表示
- Git 情報が利用できない場合の明示

## Performance

Git history の全件走査を毎回行わない。対象 Scope と必要期間を限定し、同一解析内で重複 query を避ける。

大規模 Repository では以下を確認する。

- Branch Diff の応答性
- history query の所要時間
- cancellation
- partial result
- Repository サイズに応じた上限や設定の必要性

## Acceptance Criteria

- [x] Branch Diff Scope を選択できる
- [x] base branch との差分ファイルを解析できる
- [x] Large Diff Finding を生成できる
- [x] changed lines が Finding へ含まれる
- [x] Change frequency を取得できる
- [x] Author count を取得できる
- [x] Long-lived TODO の経過情報を表示できる
- [x] Hotspot を算出し、構成根拠を説明できる

- [x] Copy for AI に必要な Git metrics を含められる
- [x] VCS 未設定時も v0.1/v0.2 の非Git機能を利用できる

## 完了記録（2026-08-15）

全 Acceptance Criteria を満たし、v0.3 を完了とする。実装は PR #19〜#21
（Branch Diff + Large Diff、Git history + Long-lived TODO、Hotspot）。

検証状況:

- 自動検証: :core 107 / :plugin 58 tests（diff / log / blame の pure parser、
  enrichment の同一性劣化、Hotspot スコア）、Plugin Verifier 両ターゲット Compatible
- 手動検証: 2 つの実 Repository で Branch Diff の意味論（merge-base +
  作業ツリー込み）、Large Diff の陽性（閾値 50 で 5 件）と Copy 出力、
  base branch 不明時の理由表示と結果クリア、Git evidence（11 commits / 2
  authors）、未コミット行の blame（age 0）、履歴 4 ヶ月前の Repository での
  劣化（evidence 非表示・エラーなし）、Hotspot（予測どおり 11 × 2 = 22 の
  説明可能スコア）、カラムソート

実地確認から出た修正（PR #19 内）:

- Scope 解決失敗が per-analyzer failure ×9 に化けていた問題 → run 全体の
  理由付き失敗として伝播
- Kotlin 合成アクセサ・enum メンバー・companion・明示 getter・テストソースが
  Unused Candidate / 依存グラフを汚染 → 除外（AnalyzedFile.isTestSource 新設）
- 失敗時に前回結果が残る / フォーカスが検索窓に飛ぶ UX → 解析開始時に
  クリアし、フォーカスはテーブルへ

既知の制約:

- multi-repo project は最初の Git repository のみ
- project base ≠ repository root の場合、履歴 enrichment は不一致分を
  素通し（誤マッピングはしない）
- Marker age は行の最終更新時点（blame の意味論）であり導入時点ではない
- Long-lived TODO の陽性（閾値超）は手元に古いコミット済み TODO が無く
  実機未観測。unit test（境界含む）で担保

Exit review の残課題: Hotspot が実レビューで「見るべきファイルの絞り込み」に
効くかは実運用で評価する。スコアが飾りになっている場合は v0.4 相当の作業より
先に Evidence 表示とスコア定義を改善する（本文の方針どおり）。

- base / feature branch の差分 fixture
- rename を含む差分
- large diff threshold
- 履歴の少ない / 多いファイル
- 複数 author
- TODO の履歴情報
- Hotspot score の再現性
- VCS 未設定 project

## Non-goals

- Remote GitHub API 連携
- Pull Request API 連携
- CI 結果取得
- Review comment 投稿
- JavaScript / TypeScript 構造解析の拡張
- 複雑な機械学習ベースの risk score

## Exit review

実レビューで「変更量・変更頻度・構造的 Finding」を組み合わせることで、見るべきファイルを絞れるか評価する。Hotspot が単なる派手な数字になっている場合は、v0.4 より先に Evidence 表示とスコア定義を改善する。
